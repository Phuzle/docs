title: "Relay Streams: receive webhooks on your server"
description: Point GitHub, Stripe and others at a Relay topic and receive the events in your own code or on your laptop, with no public URL.

<Callout type="info" title="At-least-once, with a window">
	Events wait for your server while it is away, for your plan's retention (Free 1 hour, Pro 24 hours, Team 7
	days), and are redelivered until you acknowledge them. Past that window they are dropped and your server is told.
	An event can arrive twice, so handle repeats by `id`. There is no exactly-once, and ordering holds for a single
	connection.
</Callout>

A topic can send its events to **phones** (a notification) and to **servers** (the raw webhook). A server
subscribes with one long-lived connection that it opens itself, so there is nothing to host, no tunnel, and no
public address: it works from a laptop, a container behind NAT or a CI job.

```
GitHub ──webhook──▶ Relay topic ──▶ your phone (notification)
                              └──▶ your server (raw event, kept until you acknowledge it)
```

## 1. Turn on "Servers" for an integration

Add an integration to a topic as usual (GitHub, GitLab, Stripe, Sentry, any JSON webhook…). In **Send the events
to**, switch **Servers** on (you can leave **Phones** on too). The generic webhook can be servers-only, with no
mapping to write.

## 2. Create a key that can receive

**API keys → New key → Can receive events from**: all topics, or one. (A key can also send, or only receive.)

## 3. Subscribe

```ts
import { Relay } from "@phuzle/relay";

const relay = new Relay({ apiKey: process.env.RELAY_API_KEY! });
const sub = relay.topic("acme-github-api").subscribe({ name: "deploy-bot" }); // key from RELAY_CONSUMER_KEY

for await (const ev of sub) {
  if (ev.type === "push") await deploy(ev.json());
}
```

The **consumer key** is a 43-character secret that you create once and keep with your other secrets:

```bash
relay key            # prints a new consumer key
export RELAY_CONSUMER_KEY=…
```

It derives the consumer's encryption key. Relay seals every event to it, stores only the public half, and cannot
open anything itself. Every process that uses the same **name** and key is the same consumer. Lose the key and
you create a new one; events already sealed to the old one cannot be opened.

### What an event looks like

| Field | |
|---|---|
| `id` | Relay's id for the event (use it to de-duplicate) |
| `source`, `type` | `github` + `push`, `stripe` + `invoice.paid`, … |
| `deliveryId` | the provider's own delivery id when it sends one |
| `headers` | descriptive headers of the original request, such as `x-github-event` and `x-hub-signature-256` (never credentials) |
| `body`, `json()` | the original body, byte for byte, and its parsed form |
| `seq`, `attempt` | the topic's sequence number, and how many times it has been handed out |
| `truncated` | the body was over your plan's event limit and is not included |

The SDK reconnects on its own (backoff with jitter, a heartbeat watchdog) and keeps going until you call
`sub.close()`. Listen for `sub.on("reconnecting", …)` if you want to log it.

## Acknowledging, retries and replay

Relay keeps each event for your consumer until you **acknowledge** it. By default the SDK does that for you: an event
counts as handled when your `for await` loop moves on to the next one, so if your handler throws, the event is not
acknowledged and **comes back** (with `attempt` 2, 3, …). Restart your server and it resumes where it stopped.

```ts
const sub = relay.topic("acme-github-api").subscribe({
  name: "deploy-bot",
  ack: "manual",      // only ev.ack() counts; "auto" is the default
  prefetch: 20,       // events out for handling at once; Relay sends no more until you acknowledge some
  lease: 30,          // seconds to acknowledge before the event is delivered again
  from: "last-acked", // or "latest" to skip what is waiting, or a sequence number to replay from
});
for await (const ev of sub) {
  await handle(ev);
  await ev.ack();     // or ev.nack() to hand it back at once
}
sub.on("gap", (g) => log(`missed ${g.count} events (#${g.fromSeq}–${g.toSeq}): ${g.reason}`));
```

| | |
|---|---|
| `ev.seq` | the topic's running sequence number for the event |
| `ev.attempt` | how many times it has been handed out |
| `from: 12` | replays everything from #12 that is still inside your retention, acknowledged or not |
| `gap` | events were dropped before you took them: `expired` (you were away longer than retention) `overflow` (your backlog passed your plan's cap) or `egress` (you used the day's data allowance) |

**Scaling out:** start several processes with the same consumer name and key and they share the events like a work
queue: each event goes to one of them, and if a process dies without acknowledging, the others get its events. Order is
then per process, not global.

## On your laptop: a webhook tunnel

```bash
relay listen --topic acme-github-api --forward http://localhost:3000/webhooks/github
```

Each event is printed and replayed to your local server **with the original headers**, so GitHub's, Stripe's and
Octokit's own verification and SDKs keep working. Point the provider at your Relay integration's URL once; after
that your laptop just needs to run the command. The first run creates a consumer key under `~/.relay/consumers`
for you.

## Filter, cut down and collapse

Tell Relay what you want and unwanted events cost nothing: they aren't stored, sent or counted.

```ts
const sub = relay.topic("acme-github-api").subscribe({
  name: "deploy-bot",
  filter: {
    types: ["push", "pull_request"],                              // only these events
    where: [{ path: "ref", op: "equals", value: "refs/heads/main" }], // every condition must hold
    ignoreWhen: [{ path: "repository.fork", op: "equals", value: "true" }],
    project: ["ref", "repository.full_name", "commits[].message"],    // keep only these parts of the body
    collapseKey: "{{repository.full_name}}:{{ref}}",                 // a newer event replaces an older waiting one
  },
});
```

On the command line: `relay listen --type push --type pull_request`.

- **Conditions** use the same operators as an integration mapping: `equals`, `not_equals`, `contains`, `exists`, `gt`, `lt`.
- **`project`** keeps only the listed paths (`a.b`, `items[].name`). The event says `projected` and the body is no longer
  the provider's original bytes, so don't verify the provider's signature on it. Headers are untouched.
- **`collapseKey`** is for state that supersedes itself (a build status, a deploy state): a newer event with the same key
  replaces an older one that is still waiting. One you are already handling is never taken away.
- Filters are registered with the consumer, and the latest registration wins, so processes that share a name should share
  a filter. They apply to events from then on.
- Large events (over 2 KB) are compressed before they are sealed, and the SDK unpacks them for you.

## Limits

| | Free | Pro | Team |
|---|---|---|---|
| Consumers per topic | 1 | 5 | 20 |
| Largest event | 64 KB | 256 KB | 256 KB |
| Kept for you while away | 1 hour | 24 hours | 7 days |
| Waiting events per consumer | 200 | 5,000 | 50,000 |
| Data stored for your consumers per day | 50 MB | 2 GB | 20 GB |

A webhook source may send up to 600 deliveries a minute to a topic that streams (60 if it only notifies phones).
Up to 3 connections can be open per consumer; they share the events. A body over the event limit is announced as
`truncated` rather than clipped.

## Privacy: what Relay can and can't see

This is **server-assisted**, not end-to-end encrypted: the provider sends Relay the webhook in the clear (Relay has
to check its signature), so Relay can read an event for the moment it passes through. It then seals it to your
consumer key in memory. Only ciphertext is stored (until you acknowledge it or retention ends) or sent. A stolen API key can open a stream
but receives ciphertext it cannot read. See [Encryption](/relay/concepts/encryption).

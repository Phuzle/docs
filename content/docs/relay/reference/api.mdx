Relay's public API is two endpoints. Everything else (topics, keys, devices) is managed in the
[console](/relay/guides/console).

- **Base URL:** `https://api-relay.phuzle.com`
- **Auth:** `Authorization: Bearer rly_…`, an API key from the console. A key can be limited to one
  topic.

<Callout title="Use the SDK or CLI unless you have a reason not to">
	Messages are end-to-end encrypted, so the request carries one encrypted envelope per phone, not
	your text. The [SDK](/relay/guides/sdk) and the [CLI](/relay/guides/cli) fetch the keys
	and do the encryption for you. Use the raw endpoints only when you are building your own client.
</Callout>

<Tabs items={["SDK", "CLI", "curl"]}>
	<Tab value="SDK">
```ts
import { Relay } from "@phuzlelabs/relay";

const relay = new Relay({ apiKey: process.env.RELAY_API_KEY! });
await relay.send({ topic: "acme-alerts", title: "Deploy failed", body: "api-3 exited 137" });
```
	</Tab>
	<Tab value="CLI">
```bash
export RELAY_API_KEY=rly_...
relay send --topic acme-alerts --title "Deploy failed" --body "api-3 exited 137"
```

	<Tab value="curl">
```bash
# 1. the public keys of the phones on this topic
curl -s "https://api-relay.phuzle.com/v1/trigger/recipients?topic=acme-alerts" \
  -H "Authorization: Bearer $RELAY_API_KEY"

# 2. send one encrypted envelope per phone (see "Build the envelopes" below)
curl -s -X POST https://api-relay.phuzle.com/v1/trigger \
  -H "Authorization: Bearer $RELAY_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: deploy-142" \
  -d @request.json
```
	</Tab>

## `GET /v1/trigger/recipients`

The phones subscribed to a topic and their public keys.

| Query | |
|---|---|
| `topic` | Full topic name, `<org>-<topic>` (required) |

```json
{
  "topicId": "…",
  "keysetVersion": "…",
  "recipients": [
    { "deviceId": "…", "idPub": "…", "encPub": "…", "bindSig": "…", "keysetVersion": 1 }
  ]
}
```

The response carries an `ETag` (the `keysetVersion`). Send it back as `If-None-Match` to get `304`
when nothing changed. Check each recipient's `bindSig` before encrypting to it.

## `POST /v1/trigger`

Send an encrypted notification. Responds `202`.

| Field | Type | |
|---|---|---|
| `topic` | string | required |
| `messageId` | string | required, a ULID; the same id is inside each envelope |
| `priority` | `min` `low` `default` `high` `urgent` | default `default` |
| `ttlSeconds` | integer | how long to keep trying, default 24 h, max 28 days |
| `collapseKey` | string | a newer message with the same key replaces an older one |
| `envelopes` | `{ deviceId, enc, ct }[]` | required, one per phone |

Add an `Idempotency-Key` header to make retries safe for 24 hours: a repeat returns the first
result with `duplicate: true` and sends nothing.

```json
{ "messageId": "01J…", "accepted": 2, "rejected": [], "missing": [], "keysetVersion": "…", "duplicate": false }
```

- `accepted`: phones queued for delivery.
- `rejected`: envelopes that were skipped, each with a `reason` (see [Errors](/relay/reference/errors)).
- `missing`: active phones you sent no envelope for, usually because one paired after you fetched
  keys. Fetch recipients again and resend once; the SDK does this for you.

## Build the envelopes

Each envelope is the [message](/relay/reference/message-schema) sealed to one phone with HPKE.
The exact steps and test vectors are in [Encryption](/relay/concepts/encryption).

## Limits

- A plan has a daily trigger cap per organization; going over returns `429 quota_exceeded` with
  `Retry-After`. See [Plans and limits](/relay/concepts/limits).
- Each key also has a short burst limit; a `429` always includes `Retry-After` (seconds).
- Request bodies are capped at 1 MB; the plaintext message at 2 KiB.

Errors are described in [Errors](/relay/reference/errors).

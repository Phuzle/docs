title: Trigger API
description: Send a notification with curl, the SDK or the CLI. This is the whole public API.

Relay's public API is two endpoints to send, plus [three to discover and create topics](#topics-and-devices) and one last-resort alternative ([below](#post-v1triggerpush-last-resort)). Everything else (members, keys, billing) is managed in the
[console](/relay/guides/console).

- **Base URL:** `https://relay.phuzle.com`
- **Auth:** `Authorization: Bearer rly_…`, an API key from the console. A key can be limited to one
  topic, and can be allowed to create topics.

<Callout title="Use the SDK or CLI unless you have a reason not to">
	Messages are end-to-end encrypted, so the request carries one encrypted envelope per phone, not
	your text. The [SDK](/relay/guides/sdk) and the [CLI](/relay/guides/cli) fetch the keys
	and do the encryption for you. Use the raw endpoints only when you are building your own client.
</Callout>

<Tabs items={["SDK", "CLI", "curl"]}>
	<Tab value="SDK">
```ts
import { Relay } from "@phuzle/relay";

const relay = new Relay({ apiKey: process.env.RELAY_API_KEY! });
await relay.send({ topic: "acme-alerts", title: "Deploy failed", body: "api-3 exited 137" });
```
	</Tab>
	<Tab value="CLI">
```bash
export RELAY_API_KEY=rly_...
relay send --topic acme-alerts --title "Deploy failed" --body "api-3 exited 137"
```
	</Tab>
	<Tab value="curl">
```bash
# 1. the public keys of the phones on this topic
curl -s "https://relay.phuzle.com/v1/trigger/recipients?topic=acme-alerts" \
  -H "Authorization: Bearer $RELAY_API_KEY"

# 2. send one encrypted envelope per phone (see "Build the envelopes" below)
curl -s -X POST https://relay.phuzle.com/v1/trigger \
  -H "Authorization: Bearer $RELAY_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: deploy-142" \
  -d @request.json
```
	</Tab>
</Tabs>

## Topics and devices

The same API key can look around, so scripts don't need topic names hard-coded.

| Endpoint | What it does |
|---|---|
| `GET /v1/trigger/topics` | The topics this key may send to: `{ data: [{ id, slug, fullName, name, description, devices, createdAt }], canCreate }`. `fullName` is what you pass as `topic`. A key limited to one topic sees only that one. |
| `POST /v1/trigger/topics` | Create a topic: `{ slug, name, description? }` → `201` with the topic. Needs **Can create topics** on the key. Counts against your plan's topic limit. A key limited to specific topics is allowed to send to the topics it creates. |
| `GET /v1/trigger/topics/{topic}/devices` | The phones receiving a topic (`{topic}` is the full name): nickname, model, platform, app version, last seen, when they subscribed. Never keys or tokens. The key must be allowed to send to the topic. |

Errors: `403 scope_denied` (the key isn't allowed to create topics, or to see that topic), `403 topic_limit`
(your plan's topics are used up), `403 scope_limit` (the key already holds 20 permissions), `409 slug_taken`,
`400 bad_slug`. Creating is also rate limited to 20 topics an hour per key.

## `GET /v1/trigger/recipients`

The phones subscribed to a topic and their public keys.

| Query | |
|---|---|
| `topic` | Full topic name, `<org>-<topic>` (required) |

```json
{
  "topicId": "…",
  "keysetVersion": "…",
  "recipients": [
    { "deviceId": "…", "idPub": "…", "encPub": "…", "bindSig": "…", "keysetVersion": 1 }
  ]
}
```

The response carries an `ETag` (the `keysetVersion`). Send it back as `If-None-Match` to get `304`
when nothing changed. Check each recipient's `bindSig` before encrypting to it.

## `POST /v1/trigger`

Send an encrypted notification. Responds `202`.

| Field | Type | |
|---|---|---|
| `topic` | string | required |
| `messageId` | string | required, a ULID; the same id is inside each envelope |
| `priority` | `min` `low` `default` `high` `urgent` | default `default` |
| `ttlSeconds` | integer | how long to keep trying, default 24 h, max 28 days |
| `collapseKey` | string | a newer message with the same key replaces an older one |
| `envelopes` | `{ deviceId, enc, ct }[]` | required, one per phone |

Add an `Idempotency-Key` header to make retries safe for 24 hours: a repeat returns the first
result with `duplicate: true` and sends nothing.

```json
{ "messageId": "01J…", "accepted": 2, "rejected": [], "missing": [], "keysetVersion": "…", "duplicate": false }
```

- `accepted`: phones queued for delivery.
- `rejected`: envelopes that were skipped, each with a `reason` (see [Errors](/relay/reference/errors)).
- `missing`: active phones you sent no envelope for, usually because one paired after you fetched
  keys. Fetch recipients again and resend once; the SDK does this for you.

## `POST /v1/trigger/push` (last resort)

<Callout type="warn" title="Do not use this unless you have no other choice">
	Here you send your message in **plaintext** and Relay's servers encrypt it for each phone. That
	means **Relay can read the message while it handles your request**. It is not stored or logged,
	but it is **not end-to-end encrypted**, and the phone marks it with a *Server-assisted* badge.
	The [SDK](/relay/guides/sdk) and [CLI](/relay/guides/cli) encrypt on your machine so Relay never
	sees your content. Use this only when you truly cannot run either (for example a device that can
	only make a plain HTTP request) and you accept that trade-off.
</Callout>

It exists so a plain `curl` can send a notification. It is **off by default**: an owner or admin
must turn on **Server-side encryption** under *Settings* in the console first, otherwise you get
`403 server_side_push_disabled`. You also opt in explicitly on every
request with `acknowledgeServerSideEncryption: true`; without it you get `400 acknowledgement_required`
and nothing is sent.

```bash
curl -s -X POST https://relay.phuzle.com/v1/trigger/push \
  -H "Authorization: Bearer $RELAY_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: deploy-142" \
  -d '{
    "topic": "acme-alerts",
    "acknowledgeServerSideEncryption": true,
    "title": "Deploy failed",
    "body": "api-3 exited 137",
    "priority": "high"
  }'
```

| Field | Type | |
|---|---|---|
| `topic` | string | required |
| `acknowledgeServerSideEncryption` | `true` | required: you accept that Relay can read this message |
| `title` | string | required, up to 120 characters |
| `body` | string | up to 1000 characters |
| `priority` | `min` `low` `default` `high` `urgent` | default `default` |
| `icon` | string | a built-in icon name such as `rocket`, `flame`, `bug` (see the [message schema](/relay/reference/message-schema)) |
| `url` | string | https only; the notification opens the message and then this link in an in-app browser |
| `tags` | string[] | up to 5, 24 characters each |
| `group` | string | notifications with the same group stack |
| `actions` | object[] | up to 3 buttons, each with a `label` and either a `link` (opens a page) or a `request` (sent from the phone), as in the [message schema](/relay/reference/message-schema) |
| `ttlSeconds`, `collapseKey` | | as for `POST /v1/trigger` |

It follows the same rules as the normal endpoint (the same validation as the SDK, the 2 KiB
message cap, your daily quota and `Idempotency-Key`). The `202` response has the same fields as
`POST /v1/trigger`, plus `serverEncrypted: true` and a `notice` repeating the warning, and the
`X-Relay-Encryption: server` header. Extra errors: `400 invalid_message`, `413 payload_too_large`
and `409 no_recipients` (no phone is paired to the topic yet).

## Build the envelopes

Each envelope is the [message](/relay/reference/message-schema) sealed to one phone with HPKE.
The exact steps and test vectors are in [Encryption](/relay/concepts/encryption).

## Limits

- A plan has a daily trigger cap per organization; going over returns `429 quota_exceeded` with
  `Retry-After`. See [Plans and limits](/relay/concepts/limits).
- Each key also has a short burst limit; a `429` always includes `Retry-After` (seconds).
- Request bodies are capped at 1 MB; the plaintext message at 2 KiB.

Errors are described in [Errors](/relay/reference/errors).

```json
{ "error": "Daily trigger limit reached", "code": "quota_exceeded" }
```

Validation errors add `details: [{ path, message }]`. Server errors never expose internals. A
`429` always carries a `Retry-After` header in seconds.

## HTTP errors

| Status | `code` | What to do |
|---|---|---|
| `400` | | The request body is invalid; `details` says which field. |
| `401` | `bad_api_key` | The key is missing, wrong, revoked or expired. Create a new one in the console. |
| `403` | `scope_denied` | The key is limited to other topics. Use a key for this topic or for all topics. |
| `404` | | The topic doesn't exist in your organization. |
| `413` | | The request body is over 1 MB. |
| `429` | `quota_exceeded` | The daily cap for your plan is reached. Retry after `Retry-After`, or upgrade. |
| `429` | | Too many requests in a short burst. Retry after `Retry-After`. |

## Per-phone results

A `202` can still mention phones that were skipped. Each entry in `rejected` has a `reason`:

| `reason` | Meaning |
|---|---|
| `unknown_device` | The envelope names a phone that isn't on this topic. Refetch recipients. |
| `device_inactive` | The phone was removed or deactivated. |
| `duplicate` | Two envelopes for the same phone. Only the first is used. |

Phones in `missing` had no envelope, usually because they paired after you fetched keys. Refetch
recipients and resend once.

## In the SDK

`RelayError` carries `status`, `code` and, for `429`, `retryAfterSeconds`. A message over 2 KiB is
refused before anything is sent, with `PayloadTooLargeError`.
